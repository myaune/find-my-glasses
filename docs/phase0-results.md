# Phase 0 결과 — 모델 기술검증

> 2026-09-11. 측정 코드는 `poc/`, 원시 결과는 `runs/` (gitignore).
> 데이터: 사진 19장(안경 있음 17 / 없음 2) + 영상 1개(8.2초).

## 결론 요약

기획서 10절이 최대 리스크로 꼽은 **"얼굴 없이 놓인 안경을 zero-shot 으로
잡는가"** 에 대한 답은 **잡는다** 이다. 접기로 했던 기준(3장 중 0장)과는
반대편이고, 여유도 크다.

크기는 100MB 목표를 못 맞춘다. 스토어 제약 150MB 는 통과한다.

실기기 레이턴시와 세션 성공률은 아직 판정할 수 없다.

## 확정된 것

| 항목 | 결과 |
|---|---|
| 모델 | **Grounding DINO Tiny** (Apache-2.0) |
| 프롬프트 | **`eyeglasses`** |
| 운영 임계값 | **0.40~0.45** |
| 배포 포맷 | ONNX FP16, 텍스트 인코더 제거 |
| 파일 크기 | **124.6 MB** (gzip 111.9 MB) |

## 1. 검출 성능 (0a, FP32 PyTorch)

사진 17장(안경 있음) + 2장(네거티브 컨트롤).

| 프롬프트 | 검출 | 오탐 | 분리도 |
|---|---|---|---|
| **eyeglasses** | **17/17** | **0/2** | **+0.519** |
| spectacles | 17/17 | 0/2 | +0.319 |
| ensemble_score | 17/17 | 0/2 | +0.290 |
| a pair of eyeglasses | 17/17 | 0/2 | +0.102 |
| glasses | 16/17 | 0/2 | +0.000 |

분리도 = (안경 있는 사진의 최저 점수) − (안경 없는 사진의 최고 점수).
양수면 오탐 없이 전부 잡는 임계값이 존재한다.

`eyeglasses` 는 네거티브 컨트롤에서 점수가 **정확히 0** 이다. 잡동사니
가득한 책장과 이불 널린 방을 보고도 안경이라고 하지 않았다. 대신 실제
컵에 `cup`, 휴대폰 상자에 `remote control` 이 붙었다 — 네거티브 어휘가
설계대로 흡수하고 있다.

### 기획서와 달랐던 점

기획서 5절은 O365 클래스명과 일치한다는 이유로 `glasses` 를 1순위로
지목했다. **실측에서는 꼴찌다.** 한 장을 놓치고 분리도가 0 이다.
`eyeglasses` 로 바꾼다.

프롬프트 앙상블도 개별 프롬프트보다 못하다. `eyeglasses` 단독(+0.519)이
앙상블(+0.290)을 이긴다. 약한 프롬프트를 섞으면 평균으로 끌려내려간다.

### 모델 비교

| | 분리도 | 검출 | 레이턴시(RTX 3070) |
|---|---|---|---|
| Grounding DINO Tiny | **+0.519** | 17/17 | 289 ms |
| OWLv2 base | +0.139 | 17/17 | 452 ms |

OWLv2 도 다 잡지만 여유가 좁다. 임베딩 앙상블(+0.127)도 최고가 아니었다.
정확도·속도·크기 전부 Grounding DINO 가 앞서므로 YOLO-World 는 돌리지
않았다.

## 2. 조건별 한계

촬영 사진의 거리를 박스 크기로 역산하니 중앙값 0.30m, 최대 1.49m 였다.
실사용 구간(팔 길이~1.5m)과 일치하지만 그 이상이 비어 있어, 사진을 축소해
시뮬레이션했다 (`poc/scripts/make_degraded.py`).

| 조건 | 검출 @0.25 |
|---|---|
| 원본 (0.15~1.49m) | 17/17 |
| ~1m | 15/15 |
| **~1.5m** | **17/17** |
| ~2m | 11/17 |
| ~3m | 10/17 |
| 모션 블러 | 16/17 |
| 저조도 (밝기 1/4) | 16/17 |

**실효 탐지 거리는 1.5m.** 기획서 10절 추정(1.5~2m)보다 짧지만 유스케이스
안쪽이다. 이 앱은 "여기 어디쯤 뒀는데 안 보여서 못 찾는" 상황을 다루지
방 건너편 수색이 아니다.

저조도는 거의 영향이 없다. 모션 블러는 검출은 버티지만 **안경 없는 사진의
점수를 0.000 → 0.302 로 올린다.** 흐려진 잡동사니가 안경처럼 보이기
시작한다. 기획서 9절의 temporal filter(3회 연속)와 4절의 스윕 속도 안내가
실제로 필요하다는 확인이다.

거리 시뮬레이션의 한계: 각크기만 바꿨을 뿐 원근 변화·새로운 가림·초점
변화는 재현하지 않는다. 패딩은 원본을 반사한 합성 영역이다.

## 3. 배포 포맷 (0b)

### 텍스트 인코더 제거

기획서 6절의 전제대로 동작한다. `GroundingDinoModel.forward` 에서 인코더로
넘어가는 텍스트 값은 네 개뿐이라, BERT 를 미리 계산한 값을 돌려주는 스텁으로
갈아끼우면 나머지 코드를 건드리지 않고 빠진다.

```
PyTorch 전체        657.1 MB
텍스트 인코더 제거    241.7 MB   (BERT 415.4 MB 제거)
ONNX FP32          246.1 MB   (그래프 오버헤드 4.4 MB)
ONNX FP16          124.6 MB
gzip 후             111.9 MB
```

가중치는 엔트로피가 높아 압축이 10% 밖에 안 된다. AAB 다운로드 크기도
111.9 MB 로 잡아야 한다.

### FP16 이 정확도를 깎는가 — 깎지 않는다

기획서 11절이 경고한 "FP32 에서 되던 게 배포 포맷에서 반토막 나는" 함정은
발생하지 않았다.

| | 검출 @0.40 | 오탐 | 분리도 |
|---|---|---|---|
| FP32 ONNX | 17/17 | 0/2 | +0.079 |
| **FP16 ONNX** | **17/17** | **0/2** | **+0.071** |

사진별 점수 차이는 최대 0.008 이다. 양자화 비용은 사실상 없다.

다만 **전처리 차이는 있다.** ONNX 는 입력이 800×800 으로 고정돼 있어
letterbox 를 쓰는데, 이것 때문에 네거티브 컨트롤 점수가 0.000 → 0.387 로
올랐다. 분리도가 +0.519 에서 +0.079 로 좁아진 원인은 양자화가 아니라
여기다. 여전히 양수라 운영 가능하지만 여유가 줄었다.

→ Phase 1 에서 입력 해상도를 960~1280 으로 올려 재확인할 것.

### 변환에서 막혔던 것

Grounding DINO 를 ONNX 로 내보내는 데 세 군데서 막혔고 전부 우회했다.
모델 구조가 거부한 곳은 없었다. 우려했던 deformable attention 은
`grid_sample` 로 정상 변환됐다.

1. `inference_mode` 로 만든 텐서는 트레이싱에 못 쓴다 → `no_grad`
2. `aten::isin` 이 opset 17 에 없다 → 프롬프트가 고정이라 마스크 생성
   결과를 상수로 대체
3. FP16 변환기가 비교 연산의 한쪽 입력만 바꿔 타입이 깨진다 → 전부 fp16 으로
   변환한 뒤 섞인 지점을 통일하는 수리 패스 (`poc/scripts/onnx_fp16.py`)

3번은 Swin 백본을 FP16 ONNX 로 바꿀 때 일반적으로 나오는 문제라, Phase 1
에서도 같은 수리 패스를 쓰게 된다.

## 4. Go/No-Go 대조

| 기준 | 목표 | 실측 | |
|---|---|---|---|
| 세션 성공률 (15초, ≤2m) | ≥ 80% | 1/1 | **표본 부족** |
| 오탐 | ≤ 1회/30초 | 0회 | 표본 부족 |
| 프레임 레이턴시 (실기기) | ≤ 500 ms | 미측정 | **미측정** |
| 모델 크기 | ≤ 100 MB | 124.6 MB | **초과** |

### 판정

핵심 리스크는 해소됐다. 사진 축에서는 근거가 충분하다.

남은 두 항목은 성격이 다르다.

**세션 성공률** — 영상이 1개뿐이라 통계가 아니다. 다만 사진 17장이
17/17 이고 영상에서도 5.4초에 발화했으므로, 실패를 예상할 근거는 없다.
스윕 영상 3개를 찍으면 바로 판정된다.

**실기기 레이턴시** — 이게 진짜 미지수다. 데스크탑 수치는 이렇다.

```
PyTorch CUDA (RTX 3070)    289 ms
ONNX Runtime CPU (i7-10700)  3.1 s (FP32) / 3.6 s (FP16)
```

CPU 에서 FP16 이 오히려 느린 것은 정상이다 — x86 CPU 에 fp16 연산기가 없어
fp32 로 올려서 계산한다. 모바일 GPU/NNAPI 에서는 반대가 된다.

**모바일 SoC 에서 얼마가 나올지는 모른다.** 데스크탑 CPU 3초라는 숫자만
보면 불안하고, 기획서 17절이 Phase 1 을 분리해둔 이유가 이것이다.
500ms 예산(2 FPS)을 못 맞추면 입력 해상도를 낮추거나 INT8 로 가야 하는데,
둘 다 검출 성능을 깎으므로 지금 확보한 여유(분리도 +0.071)를 얼마나
쓸 수 있는지가 관건이다.

### 100MB 를 어떻게 할 것인가

124.6 MB 는 100MB 목표를 25% 초과하지만 150MB 스토어 제약은 통과한다.
앱 나머지를 15~35 MB 로 잡으면 총 127~147 MB 다.

기획서 6절이 남겨둔 INT8 카드를 쓰면 60MB 대로 내려간다. 다만 INT8 은
작은 물체에 비대칭적으로 타격을 주고 안경이 정확히 그 작은 물체다.
**레이턴시 때문에 INT8 이 필요해지면 그때 함께 재측정한다.** 크기만을
이유로 먼저 꺼낼 필요는 없다.

## 5. 측정의 한계

- **네거티브 컨트롤이 2장뿐이다.** 오탐 0 은 "2장에서 안 났다" 이상의
  의미가 없다.
- **영상이 1개(8.2초)뿐이다.** 세션 성공률은 통계가 아니다.
- **정답 박스가 없다.** 박스가 실제로 안경 위에 있는지는 `runs/*/annotated/`
  를 눈으로 확인했다. 자동 검증이 아니다.
- **세션 판정에 자이로가 없다.** 실제 앱은 카메라 모션을 보상한 좌표계에서
  association 하지만(기획서 9절), 오프라인 영상에는 자이로가 없어 화면 좌표
  IoU 로만 묶었다. 실제보다 보수적으로 나온다.
- **실기기 측정이 전혀 없다.**
