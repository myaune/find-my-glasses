# 안경 찾기 앱 — 제품/기술 기획서

> v2 (2026-09-11). v1은 git 이력 참조 (commit a6f6eb5).

## 1. 한 줄 정의

**안경을 벗어서 안경이 보이지 않을 때, 스마트폰 카메라가 대신 안경을 찾아
화면 위에 위치를 표시해주는 온디바이스 앱.**

## 2. 해결하려는 문제

열쇠나 지갑은 찾는 사람이 정상적으로 볼 수 있지만, 안경은 분실 순간
사용자의 시력 자체가 떨어져 있다.

1. 사용자가 안경을 벗어 두었다
2. 다시 쓰려고 하는데 위치가 기억나지 않는다
3. 안경이 없어서 주변의 안경을 시각적으로 식별하기 어렵다
4. 스마트폰은 얼굴 가까이 가져가 조작할 수 있다
5. 스마트폰 카메라와 객체 탐지가 사용자의 시각을 대신한다

핵심 메시지는 **"안경이 없어서 안경을 못 찾는 문제"** 하나에 집중한다.

## 3. 제품 원칙

- 핵심 타깃은 `eyeglasses` 하나
- 커스텀 데이터셋 제작, annotation, fine-tuning 없음
- 사용자가 자기 안경을 등록할 필요 없음
- pretrained open-vocabulary detector 사용
- 영상과 추론은 100% 로컬 처리, 서버 inference/API 없음
- 회원가입 없음
- 모델은 앱에 번들 — 추가 다운로드 없이 오프라인 즉시 동작
- UI는 사용자가 안경을 쓰지 않았다는 것을 전제로 설계

## 4. 핵심 UX

```
앱 실행
→ [👓 안경 찾기]
→ 카메라 실행 + 전체 라이브 프리뷰
→ "천천히 주변을 비춰주세요"
→ 로컬 객체 탐지
→ 검출 위치에 굵은 색 네모 + 주변 화살표들이 네모를 가리킴
→ 화면 밖으로 나가면 가장자리 큰 화살표가 방향 유지
→ 확신도가 올라갈수록 색·텍스트·펄스·진동 강화
→ [찾았다!] 버튼
```

### 화면 구성

```
┌─────────────────────────┐
│  ↘      라이브 프리뷰      │  전체 화면, 카메라 그대로
│                         │
│        ┏━━━━━━┓          │  검출 위치에 굵은 색 네모
│    →   ┃      ┃   ←      │
│        ┗━━━━━━┛          │  주변 화살표들이 네모를 가리킴
│           ↑             │
│      "여기이이이!"         │
├─────────────────────────┤
│       배너 광고            │
└─────────────────────────┘
```

확대 크롭은 하지 않는다. 사용자는 폰을 들고 실제로 걸어다니며 찾으므로,
화면은 **위치를 지정**하는 역할만 한다.

### 확신도 표기

확신도는 색 하나에 의존하지 않고 **색 + 텍스트 + 펄스 속도** 3중으로 표기한다.
노랑 미만(확신 낮음)은 아예 표시하지 않는다.

| 확신도 | 네모 색 | 텍스트 | 펄스 | 진동 |
|---|---|---|---|---|
| 낮음 | 노랑 | "아마도...?" | 느리게 | 약 |
| 중간 | 주황 | "여기 같아요" | 보통 | 중 |
| 높음 | **빨강** | **"여기이이이!"** | 빠르게 | 강 |

### 화면 밖 방향 유지 (자이로 앵커링)

폰을 들고 이동하다 보면 안경이 화면에서 벗어난다. 검출 순간의 기기 자세를
함께 저장해 월드 좌표에 앵커링하고, 화면 밖일 때는 가장자리 큰 화살표가
그 방향을 계속 가리킨다. **이것이 없으면 화면을 벗어나는 순간 정보가 증발한다.**

### 스윕 속도 안내

자이로 각속도로 회전 속도를 측정한다.

- 화각 약 65°, 2 FPS에서 프레임 간 화면이 겹치려면 프레임당 회전 ≤ 32°
- 즉 **≤ 64°/s**. 권장 **30~40°/s** = 방 한 바퀴(360°)를 약 10초
- 초과 시 음성 "조금만 천천히" + 짧은 진동
- 햅틱 메트로놈으로 적정 페이스 유도

속도 제한은 UX 안내이면서 동시에 **모션 블러로 인한 recall 저하를 막는 수단**이다.

### 접근성 전제

- 큰 고대비 도형과 색은 노안 사용자도 잘 보인다. 작은 글씨만 못 본다 → **텍스트 최소화**
- 음성 안내는 시력 때문이 아니라 **화면 대신 방을 보면서 쓸 수 있게** 하기 위해 넣는다

## 5. AI 기술 요구사항

필수 조건:

- Zero-shot / open-vocabulary object detection
- Custom training 없음
- Bounding box 반환
- 완전 로컬 inference
- Android/iOS 배포 가능
- **모델 최종 크기 ≤ 100MB** (Play 150MB 제한 + 앱 나머지 여유)
- **라이선스 permissive** (Apache-2.0 / MIT)

### 모델 후보

| 순위 | 모델 | 라이선스 | 비고 |
|---|---|---|---|
| 1 | **Grounding DINO Tiny** (IDEA) | Apache-2.0 (코드+가중치) | ONNX 공개, 정확도 최상위 |
| 2 | **OWLv2** (Google) | Apache-2.0 | rare/small object 강함, INT8 선례 있음 |
| 3 | YOLO-World (Tencent) | GPL-3.0 | 속도 baseline / 폴백. Android 단독이면 실사용 가능 |
| 제외 | YOLOE·YOLO26 (Ultralytics) | AGPL-3.0 | |
| 제외 | RTMDet (OpenMMLab) | GPL-3.0 | |

**왜 YOLO-World가 1순위에서 내려왔나:** 유일한 우위가 속도인데, 이 앱은
2~3 FPS면 충분해서 속도가 남아돈다. 그 대가로 GPL을 떠안으면 App Store
배포에서 리스크가 생긴다(FSF가 GPL §6 위반으로 제기, 2010년 실제 앱 내려간
전례). 예외 허가는 저작권자만 줄 수 있어 앱 소스를 공개해도 해결되지 않는다.
Apache-2.0 후보가 정확도까지 더 높으므로 감수할 이유가 없다.

### 프롬프트

**Objects365 데이터셋에 `Glasses` 클래스가 실제로 존재한다 (index 7).**
그리고 Grounding DINO·OWLv2·YOLO-World 모두 O365를 사전학습에 사용한다.
→ 안경은 롱테일 단어가 아니라 **박스 라벨까지 붙어 지도학습된 클래스**다.

후보:

```
glasses              ← O365 클래스명과 정확히 일치. 1순위로 검증
eyeglasses
spectacles
a pair of eyeglasses
```

추가 기법 (custom training 아님, 비용 0):

- **프롬프트 앙상블** — 여러 표현의 텍스트 임베딩을 평균
- **네거티브 어휘 동시 투입** — `keys`, `phone`, `scissors`, `pen`, `remote control`, `cup`.
  단일 클래스 open-vocab은 오탐이 심하므로 경쟁 클래스를 넣으면 크게 줄어든다.
  UI에서는 숨긴다.

## 6. 성능 전략

**이 앱의 레이턴시 예산은 넉넉하다.**

사용자가 방을 10~20초간 훑는다. temporal filter가 확신하는 데 3회 검출이
필요하다면, 2 FPS로도 스윕당 20~40회 추론 기회가 있다. 안경이 화면에 들어와
있는 3~4초 동안 6~8회면 충분하다.

```
프레임 예산   500ms (2~3 FPS)
우선순위      입력 해상도(960~1280) ≫ recall ≫ 양자화 정밀도 > FPS
런타임        텍스트 인코더 제거 — 어휘가 고정 1개이므로
              텍스트 임베딩을 빌드 타임에 구워넣는다 (BERT가 통째로 빠짐)
양자화        FP16 기본. INT8은 100MB를 못 맞출 때만 꺼내는 카드
```

INT8은 필수가 아니라 경량화 수단이다. 정밀도가 뭉개져 작은 물체 검출이
특히 타격받으므로, 속도가 남는 이 앱에서는 굳이 갈 이유가 없다.

## 7. 플랫폼 — Android Native + iOS Native (둘 다 출시)

**Flutter를 쓰지 않는다.**

Flutter의 성능 병목은 UI가 아니라 *카메라 프레임을 매 프레임 Dart로 넘기는 것*인데,
우리 설계는 추론을 네이티브에서 끝내고 좌표만 올리므로 그 문제는 없다.
**Flutter를 제외하는 이유는 성능이 아니라 작업량 구조다.**

| 부분 | Flutter로 커버되나 |
|---|---|
| 카메라 프레임 취득 | ❌ 네이티브 |
| 전처리 + ONNX 추론 | ❌ 네이티브 |
| 라이브 프리뷰 출력 | ❌ 네이티브 (Texture로 넘겨야 함) |
| 화살표·네모·색 오버레이 | ✅ |
| 음성·진동·광고·IAP·설정 | ✅ |

Flutter 기본 `camera` 플러그인은 추론을 하지 않는다. 프레임 넘기기를 피하려면
"카메라 + 추론을 소유하고 프리뷰만 Texture로 내보내는" **커스텀 플러그인을
양 플랫폼에 직접 써야 한다.**

```
Flutter:  네이티브 핵심 × 2  +  플러그인/브릿지 레이어 × 2  +  UI × 1
Native :  네이티브 핵심 × 2  +  UI × 2
```

Flutter가 비싼 부분을 줄여주지 못하고 브릿지 레이어만 얹힌다. 그 대가로
아끼는 UI는 화면 4~5개다. **이 앱은 네이티브 코드 비중이 압도적이므로 Native.**

(UI가 무겁고 ML이 가벼운 앱이라면 판단이 반대가 된다. 앱별 판단이다.)

```
Android   Kotlin + Jetpack Compose + CameraX + ONNX Runtime
iOS       Swift + SwiftUI + AVFoundation + ONNX Runtime / Core ML
```

Unity는 3D·physics·scene·game-loop을 전혀 쓰지 않으면서 앱 크기·플러그인
의존·ML 런타임 연결 비용만 발생시키므로 제외한다.

## 8. 아키텍처

```
CameraX / AVFoundation
   ↓ 최신 frame (오래된 frame은 폐기)
Resize / preprocessing
   ↓
ONNX Runtime (텍스트 인코더 제거된 비전 브랜치)
   ↓ bbox + confidence
Temporal filter (자이로로 카메라 모션 보상 후 association)
   ↓
화면 좌표 변환 + 월드 앵커링
   ├→ 색 네모 + 화살표 UI
   ├→ 햅틱
   └→ 음성
```

앱 UI와 detector를 분리한다. 모델을 교체해도 제품 코드는 유지한다.

```kotlin
startSearch(ObjectType.GLASSES)

data class Detection(
    val confidence: Float,
    val centerX: Float,
    val centerY: Float,
    val width: Float,
    val height: Float,
)
```

## 9. Temporal Detection

단일 frame의 낮은 confidence만으로 알림을 내지 않는다.

```
Frame 1: glasses 0.42
Frame 2: glasses 0.55
Frame 3: glasses 0.64
Frame 4: glasses 0.70
```

비슷한 위치에서 연속 검출되면 confidence를 누적·안정화한다.

**중요:** 카메라가 움직이므로 화면 좌표 기준으로는 같은 안경이 매 프레임 다른
위치에 나타난다. **자이로로 카메라 모션을 보상한 좌표계에서 association**해야
트랙이 끊기지 않는다.

안경 찾기에서는 false positive 0%보다 **실제 안경을 놓치지 않는 것**이 중요하다.
오탐은 가서 보면 1초 만에 해소되지만, 놓치면 앱이 쓸모없어진다.

## 10. 가장 큰 기술 리스크

**① 도메인 갭 — "얼굴 없는 안경"**

학습 데이터(O365 등)에서 glasses는 압도적으로 **사람 얼굴에 씌워진 상태**다.
책상 위에 접힌 채 놓인 안경, 이불 위에 뒤집힌 안경은 학습 분포에서 벗어나 있다.
모델이 얼굴이라는 문맥 단서에 의존해 학습됐다면 recall이 급락할 수 있다.

→ **Phase 0의 첫 실험.** 검증 비용이 가장 싸다.

**② Small-object detection**

안경은 얇은 프레임, 투명 렌즈, 다양한 형태, 접힘/펼침, 배경이 그대로 비침,
멀면 극소수 픽셀.

거리별 추정 (안경 폭 ~14cm, 수평 화각 ~65°, 640px 입력 기준):

| 거리 | 입력에서 안경 폭 |
|---|---|
| 0.5m | ~130px |
| 1m | ~66px |
| 2m | ~33px |
| 3m | ~22px |

3m는 이론상 하한 근처이고 얇은 테 + 투명 렌즈가 겹치면 사실상 어렵다.
**실효 탐지 거리는 1.5~2m로 본다.** 즉 이 앱은 "문간에서 방을 스캔"이 아니라
**"폰을 들고 방을 돌아다니며 훑는" 도구**다.

## 11. PoC 검증 계획 (Phase 0)

### 사진 축

- **배경** — 흰/검은 책상, 나무/타일 바닥, 침대·무늬 이불, 소파,
  잡동사니 많은 복잡한 표면, **역광/창가**, 저조도
- **안경** — 검은 뿔테, 금속테, 투명테, 가능하면 무테 /
  펼침, 접힘, 옆으로 놓임, 뒤집힘, 일부 가림
- **거리** — 0.5m, 1m, 2m, 3m
- **오탐 유발** — 안경집 옆, 책 위, 열쇠·펜·리모컨 근처

**모든 사진은 얼굴 없이 안경만.** 리스크 ①이 핵심 검증 대상이다.

목표 60~100장.

### 실험 그리드

- 모델 3종 × 프롬프트 4종 + 임베딩 앙상블
- 네거티브 어휘 동시 투입
- 신뢰도 임계값 스윕 → recall / FP 곡선

### 측정

**프레임 단위 recall이 아니라 세션 단위 성공률로 잰다.**
프레임 recall 10%인 모델도 스윕 중 20~40번 시도하면 실사용에서는 성공한다.

- 세션 성공률 (15초 스윕 시뮬레이션)
- False-positive 빈도
- 최초 detection까지 시간
- 최대 실용 탐지 거리
- inference latency
- 모델 크기
- 저조도 성능

### 단계

| | 내용 |
|---|---|
| **0a** | FP32 PyTorch — "원리적으로 되는가" 상한선 측정 |
| **0b** | 배포 포맷(ONNX FP16) 재측정 — **이 숫자로 Go/No-Go 판정** |

FP32로 측정한 뒤 배포 포맷에서 recall이 반토막 나는 것이 고전적 함정이다.
양자화는 작은 객체에 비대칭적으로 타격을 준다.

### Go/No-Go

| 지표 | 기준 |
|---|---|
| 세션 성공률 (15초 스윕, ≤2m) | **≥ 80%** |
| 오탐 | 30초 스윕당 ≤ 1회 |
| 프레임 레이턴시 (실기기) | ≤ 500ms |
| 모델 크기 | ≤ 100MB |

> 안경을 쓰지 않은 사용자가 스마트폰으로 방을 천천히 훑었을 때,
> 일반적인 생활환경에서 15초 이내에 안경을 찾아내는가?

이 질문에 답이 나오기 전에는 전체 제품 개발을 진행하지 않는다.

## 14. 수익 / 운영

```
하단 배너 고정
[찾았다!] 버튼 → 전면 광고     ← 태스크 완료 직후. 성공했을 때만 뜬다
광고 제거 IAP $1.99 (non-consumable)
```

빈도 제한은 두지 않는다. 전면 광고가 성공 시점에만 걸려 있어 실패 후
재시도에는 뜨지 않고, 안경 분실 자체가 잦은 일이 아니다.

IAP 구현 시 **"구매 복원" 버튼 필수** (없으면 Apple 심사 리젝).
연 매출 100만 달러 미만이면 양 스토어 소규모 개발자 프로그램으로 수수료
30% → 15%.

**수익 기대치:** 실제 사용 빈도가 1~3개월에 1회 수준이고 검색 유입도
불확실하므로, 이 앱 단독의 수익은 기대치에서 제외한다.

서버가 없으므로 사용자가 늘어도 추론 비용은 발생하지 않는다.
운영 비용은 스토어 계정, 광고/분석 SDK, OS·dependency 업데이트, 실기기 QA.

## 18. 추가 물체

제품 정체성은 끝까지 **안경 찾기**에 둔다.

pretrained 모델이 잘 잡는 것에 한해 `keys`, `wallet`, `remote control` 등을
부가적으로 제공할 수 있다. 이 물건들은 사용자가 육안으로 볼 수 있으므로
핵심 가치 제안으로 취급하지 않는다.

## 19. 구현 에이전트에게 주는 지시

1. **Custom training을 제안하거나 수행하지 말 것**
2. Apache-2.0 모델(Grounding DINO, OWLv2)을 우선 검증할 것
3. 성능이 부족하면 데이터셋 제작으로 가지 말고 다른 pretrained detector를 비교할 것
4. 서버 inference/API를 추가하지 말 것
5. 카메라 영상은 로컬 처리할 것
6. Unity, Flutter를 사용하지 말 것
7. UI보다 실제 안경 recall 검증을 먼저 할 것
8. **프레임 단위 recall이 아니라 세션 단위 성공률로 판단할 것**
9. 라이선스는 실제 사용 버전의 코드와 weights를 각각 확인할 것
10. 모델 크기 100MB 제약을 항상 염두에 둘 것
11. 사용자가 안경을 쓰지 않아 화면이 잘 보이지 않는다는 것을 모든 UX 결정의 기준으로 삼을 것
